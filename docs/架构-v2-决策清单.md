## 2. 服务端结构

| 编号 | 决策点 | 结论 | 状态 |
|---|---|---|---|
| 2.1 | 分层与依赖方向 | 三层：Controller → Service → PrismaService，不设 Repository | ✅ 已定 |
| 2.2 | 模块划分粒度 | 代码按表分目录（`modules/` 一目录一张表）；`portal/`、`jobs/` 与 `modules/` 平级；Nest 模块只留根 + Prisma/Config 全局 | ✅ 已定 |
| 2.3 | 响应信封实现 | 全局 `ResponseInterceptor` + `@Raw()` 例外 | ✅ 已定 |
| 2.4 | 错误码体系 | `0` 成功 / `1` 通用失败 / `100401` 登录过期 / `100500` 服务端异常；HTTP 固定 200 | ✅ 已定 |
| 2.5 | 输入校验 | zod（env 与接口共用） | ✅ 已定 |
| 2.6 | 列表与分页约定 | `Page<T> = {list,total,pageNum,pageSize,totalPages}`，请求参数同名 | ✅ 已定 |
| 2.7 | 目录结构 | `modules/<表>/{controller,service,dto}`；目录名取 Prisma model 的 kebab；`portal/`、`jobs/` 与 `modules/` 平级 | ✅ 已定 |
| 2.8 | 命名约定 | DTO 导出名 `XxxDTO`；一表一个 controller 文件；`dto/<表名>.ts` 不带 schema | ✅ 已定 |
| 2.9 | 表的标准接口 | 全 `POST` `/api/admin/<表>/<动作>`：`create` / `update` / `delete`（`{ids}`）/ `get`（任意条件，非唯一报错）/ `page` / `all`（上限 1000）；内部表同样全开 | ✅ 已定 |

## 讨论顺序建议

依赖关系决定顺序，先定上游再定下游：

1. **第 1 组**（工程底座）——决定后面所有产物的形态，尤其 1.1 与 1.3。
2. **第 2、3 组**（服务端与数据层）——决定代码怎么写、库怎么演进。
3. **第 4、5 组**（前台与后台）——决定用户看到什么，也是工作量最大的部分。
4. **第 6、7、8 组**（采集、发布、规范）——收尾性决策。

其中 **4.1 与 5.1 互相牵制**，建议放在同一轮讨论。

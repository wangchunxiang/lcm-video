# 数据库设计 v2（逐表结论）

> 本文只记录**已确认**的结论，讨论过程留在对话里。落库形式是「在新库 `lcm-video` 里从零建表」，旧库 `lcm_video` 只作为数据来源，不再写入。

## 0. 总则

| 项 | 约定 |
|---|---|
| 库 | 新库 `lcm-video`（与旧的 `lcm_video` 在同一实例上并存）。库名含连字符，SQL 里一律写成 `` `lcm-video` `` |
| 引擎 / 字符集 | InnoDB，`utf8mb4` / `utf8mb4_unicode_ci`（与库默认一致） |
| 表名 | 保留 `lcm_` 前缀，小写下划线；`lcm_collect_task_log` 这类「父_子」结构 |
| 列名 | 小写下划线 |
| 全局列 | 每张表都有 `id`、`created_at`、`updated_at`，不允许因为它们「没人读」而删除 |
| 主键 | `id BIGINT UNSIGNED AUTO_INCREMENT`，业务键用唯一索引承载；所有引用列（`*_id`、`pid`、`category_pid`）同类型。选 BIGINT 的理由不是容量，而是**类型对齐**：TypeORM 的 mysql 驱动默认开 `supportBigNumbers + bigNumberStrings`，BIGINT 列在 JS 侧一律是 **string**，正好等于 `@ackplus/nest-crud` 的 `BaseEntity.id: string`，一处断言都不需要；而 INT 列返回的是 number，与库的约束打架。**配套约定：id 全链路按字符串处理**——不做算术、不与数字用 `===` 比较、排序交给数据库 |
| 枚举 | 一律 `TINYINT UNSIGNED` + 列注释，不使用字符串枚举 |
| 外键 | 不建物理外键。表间关联只靠列 + 索引 + 应用层保证 |
| 索引命名 | 唯一索引 `uk_*`，普通索引 `idx_*` |
| 服务端 | 实际是 **MariaDB 12.3.2**（不是 MySQL）：驱动按 `mariadb` 连接；CHECK 约束生效；`JSON` 列在 MariaDB 下是 `LONGTEXT` + `json_valid` 校验，读写按字符串处理 |
| 时间列 | `created_at` / `updated_at` 由 TypeORM 的 `@CreateDateColumn` / `@UpdateDateColumn` 维护，DDL 上是 `DEFAULT CURRENT_TIMESTAMP(6)` 与 `ON UPDATE CURRENT_TIMESTAMP(6)`；**原生 SQL** 更新行时要自己补 `updated_at = NOW()`，ORM 不会替你加 |

## 0.1 落地位置

本文是设计说明；可执行的真相源是 TypeORM 的实体与迁移：

- **实体**：`apps/server/src/modules/<表>/<表>.entity.ts`（一表一目录，列名用 `@Column({ name: 'snake_case' })` 对齐库里的下划线命名）。
- **迁移**：`apps/server/src/database/migrations/`，首个迁移是 baseline（按实体从零建 15 张表，主键 `BIGINT UNSIGNED`，末尾手工追加 `ck_status_mapped`）；之后按需增量迁移。目前 `migrations/index.ts` 注册了 **9 个**，最新是 `1794400008000-normalize-cover-host`：`1794310399174-init`、`1794400000000-vod-merge-rule`、`1794400001000-widen-release-date`、`1794400002000-source-rule-comments`、`1794400003000-merge-preview-indexes`、`1794400005000-portal-list-indexes`、`1794400006000-drop-obsolete-settings`、`1794400007000-source-rule-multi-from`、`1794400008000-normalize-cover-host`。
- **种子**：`apps/server/src/database/seeds/`，纯 SQL 文件，按文件名顺序由 `npm run db:seed`（`src/database/seed.ts`，支持 `--dry-run` 只打印语句）导入；配套 `npm run db:migrate`（跑迁移）与 `npm run db:reset`（清库重来）。
- 早期的 Prisma schema 与 drizzle schema 已删除（`packages/db` 只剩种子，后来种子也搬进 server），`_prisma_migrations` 表只存在于用旧迁移建过的库里；新库由 baseline 重建，不需要它。

## 0.2 主键改 BIGINT 的落地清单

现状：新库 `lcm-video` 由旧迁移建成，15 张表的主键与引用列都还是 `int(10) unsigned`（`lcm_play_line` 已在探针中手工改为 `bigint(20) unsigned`）。目标：全部改成 `BIGINT UNSIGNED`。

**做法**：不写 `ALTER TABLE`，直接由 TypeORM baseline 迁移按实体从零建表（库内只有种子数据，可随 baseline 重建）。若某环境必须原地改，按下表逐列 `ALTER`，顺序为先主键后引用列。

主键（15 个）：

`lcm_category` `lcm_vod` `lcm_vod_play` `lcm_collect_source` `lcm_play_line` `lcm_collect_source_category` `lcm_collect_task` `lcm_collect_task_log` `lcm_collect_task_log_detail` `lcm_admin_user` `lcm_ad_feature` `lcm_vod_merge_ignore` `lcm_source_rule` `lcm_cover_check` `lcm_setting`

引用列（13 个）：

| 表 | 列 |
|---|---|
| `lcm_category` | `pid` |
| `lcm_vod` | `category_id`、`category_pid` |
| `lcm_vod_play` | `vod_id`、`source_id`（可空） |
| `lcm_collect_source_category` | `source_id`、`category_id` |
| `lcm_collect_task` | `source_id` |
| `lcm_collect_task_log` | `task_id`、`source_id` |
| `lcm_collect_task_log_detail` | `log_id` |
| `lcm_ad_feature` | `source_id` |
| `lcm_source_rule` | `source_id` |

**不跟着改的列**（保持原类型或本来就是字符串）：

- `lcm_collect_source_category.source_type_id` / `source_type_pid`：源站自己的分类 id，`VARCHAR(50)`，不是本站主键。
- `lcm_vod_play.source_vod_id`：源站影片 id，`VARCHAR(50)`。
- 计数与枚举列（`total`、`inserted`、`sort`、`status`、`year`、`vod_count`、`hit_vods`、`interrupted_ms` 等）：保持 `INT UNSIGNED` / `TINYINT UNSIGNED`。
- 种子：`apps/server/src/database/seeds/` 下的 `lcm_category.sql`（34 行 = 4 一级 + 30 二级）、`lcm_setting.sql`（15 行 = 14 个配置键 + `merge_rules`）、`lcm_admin_user.sql`（1 个 `admin`）。
- 已导向新库 `lcm-video`：15 张业务表由 baseline 迁移重建，种子已导入，CHECK 已验证可拦截 `status=1 且 category_id=0`。

## 2. `lcm_category` — 分类，固定两层

```sql
CREATE TABLE lcm_category (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  pid         BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '父分类 id，0 表示一级分类',
  name        VARCHAR(50)     NOT NULL DEFAULT '',
  alias       VARCHAR(50)     NOT NULL DEFAULT '' COMMENT 'URL 段，如 movie',
  match_names VARCHAR(255)    NOT NULL DEFAULT '' COMMENT '源站分类名匹配串，逗号分隔，用于自动映射',
  sort        INT UNSIGNED    NOT NULL DEFAULT 0,
  is_show     TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '1 前台显示 0 隐藏',
  created_at  DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at  DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
  PRIMARY KEY (id),
  UNIQUE KEY uk_alias (alias),
  KEY idx_pid_sort (pid, sort)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

结论：整表保留。分类层级固定在两级（一级 `pid=0`，二级指向一级），不引入无限层级。

`match_names` 继续用逗号分隔的字符串，不拆成关联表——它只被自动映射按 `split(',')` 消费。

### 初始数据

建表后必须写入 34 行基础分类（4 个一级 + 30 个二级），数据取自现有 `lcm_video` 库的 `lcm_category` 表，见 `apps/server/src/database/seeds/lcm_category.sql`。

| 一级分类 (id) | 二级分类数 | 二级分类 id 段 |
|---|---|---|
| 电影 (1) | 15 | 5–19 |
| 剧集 (2) | 5 | 20–24 |
| 综艺 (3) | 5 | 25–29 |
| 动漫 (4) | 5 | 30–34 |

`id` 必须显式指定：`pid` 依赖这些编号，且影片表的 `category_id` / `category_pid` 也指向它们。`created_at` / `updated_at` 交给列默认值。

## 3. `lcm_vod` — 影片主表

```sql
CREATE TABLE lcm_vod (
  id               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  category_id      BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '二级分类 id',
  category_pid     BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '一级分类 id，冗余字段，列表按一级分类筛选时避免 join',
  name             VARCHAR(255)    NOT NULL DEFAULT '',
  name_hash        CHAR(32)        NOT NULL DEFAULT '' COMMENT '规范化片名的 MD5，严格判重用',
  name_hash_loose  CHAR(32)        NOT NULL DEFAULT '' COMMENT '去掉标点后的 MD5，仅用于后台提示疑似重复',
  sub_name         VARCHAR(500)    NOT NULL DEFAULT '' COMMENT '别名',
  cover            VARCHAR(1000)   NOT NULL DEFAULT '',
  cover_host       VARCHAR(255)    NOT NULL DEFAULT '' COMMENT '封面域名，写入 cover 时同步维护',
  actor            VARCHAR(1000)   NOT NULL DEFAULT '',
  director         VARCHAR(500)    NOT NULL DEFAULT '',
  writer           VARCHAR(500)    NOT NULL DEFAULT '',
  intro            VARCHAR(1000)   NOT NULL DEFAULT '' COMMENT '短简介，列表页用',
  content          TEXT            NULL                COMMENT '长简介，详情页用',
  remarks          VARCHAR(255)    NOT NULL DEFAULT '' COMMENT '更新备注',
  release_date     VARCHAR(255)    NOT NULL DEFAULT '' COMMENT '上映日期，源站原文，不做规范化',
  episode_count    INT UNSIGNED    NOT NULL DEFAULT 0,
  area             VARCHAR(100)    NOT NULL DEFAULT '',
  lang             VARCHAR(100)    NOT NULL DEFAULT '',
  year             INT UNSIGNED    NOT NULL DEFAULT 0,
  status           TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '1 上架 0 下架',
  collected_at     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '最后一次采集时间，列表排序用',
  created_at       DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at       DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
  PRIMARY KEY (id),
  KEY idx_category_status (category_id, status),
  KEY idx_pid_status (category_pid, status),
  KEY idx_category_status_year (category_id, status, year),
  KEY idx_pid_status_year (category_pid, status, year),
  KEY idx_name_hash (name_hash),
  KEY idx_name_hash_loose (name_hash_loose),
  KEY idx_status_collected (status, collected_at),
  KEY idx_status_created (status, created_at, id),
  KEY idx_status_year (status, year),
  KEY idx_cover_host (cover_host),
  KEY idx_search (status, name, year, collected_at, created_at),
  KEY idx_merge_preview (name_hash, name, year, status, collected_at),
  KEY idx_merge_loose (name_hash_loose, name_hash)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

改动与理由：

- **删 `letter` 与 `idx_letter`**：全仓没有任何读取方，只有采集写入和后台编辑表单写入。首字母检索没有对应界面。
- **`cover_host` 由生成列改为普通列**，`idx_cover_host` 保留：ORM 不管理 MySQL 生成列，改普通列后由写入 `cover` 的同一处代码同步维护（采集写库、后台改封面、批量换/清封面三个入口）。取值口径统一为「小写、不带端口」（`hostOf()`），旧库导入带进来的 `www.imgzy360.com:7788` 这类写法由 `1794400008000-normalize-cover-host` 一次性清洗——体检抽查会用 `hostOf(cover)` 重算域名与这一列比对，两边口径不一致时该域名会抽不到样本、误报「库里没有该域名的图片」。
- **`release_date` 保留源站原文**，长度沿用旧库的 255：旧库最长的一条 72 字符（多个日期与电影节后缀），不解析、不截断，前台原样展示。
- **`intro` 与 `content` 不合并**：列表页只读 `intro`，详情页读 `content`；合并会让列表查询背上大字段。
- **`idx_search` 保留**：搜索用 `status = 1 AND name LIKE '%kw%'` 并只取 `id / year / collected_at / created_at`（`apps/server/src/modules/portal/portal.service.ts`，查询里显式 `FORCE INDEX (idx_search)`）。前导通配符用不上索引做定位，但 `status` 能把范围收窄，且这四个列全在索引里，扫描不需要回表——删了会退化成全表扫。
- **新增 `idx_status_created` / `idx_status_year`**（迁移 `1794400005000-portal-list-indexes`，`information_schema` 判存在后 `ALTER TABLE ADD INDEX`）：「最新入库」按 `created_at` 排序，原先无索引，12 万行要 filesort（实测 7.4 秒），建索引后 24ms；年份筛选的 `SELECT DISTINCT year` 原先扫 `status = 1` 的全部行（185~450ms），有索引后 100ms 左右（再叠加进程内 60 秒缓存）。
- **`category_pid` 保留**：前台按一级分类筛选直接命中 `idx_pid_status`，不必回 `lcm_category` 找子分类。
- **新增 `idx_merge_preview` / `idx_merge_loose`**：重复影片预览要按 `name_hash` 分组后读 `name / year / status / collected_at`，原先按 1 万个哈希值 `IN` 查成员行、每行回表读 238MB 的宽表，21k 行要 12 秒；这两个覆盖索引把这一步变成索引扫描。疑似重复（`name_hash_loose`）则靠 `(name_hash_loose, name_hash)` 直接数出组内有几种严格键，只给命中的一两百组回表。

## 4. `lcm_vod_play` — 播放线路数据

```sql
CREATE TABLE lcm_vod_play (
  id                 BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  vod_id             BIGINT UNSIGNED NOT NULL DEFAULT 0,
  source_id          BIGINT UNSIGNED NULL COMMENT 'NULL 表示手工添加的线路',
  source_from        VARCHAR(50)     NOT NULL DEFAULT '' COMMENT '线路标识，如 lzm3u8',
  source_vod_id      VARCHAR(50)     NOT NULL DEFAULT '' COMMENT '源站内的影片 id，用于增量比对',
  source_updated_at  DATETIME        NULL COMMENT '源站给出的更新时间，用于判断是否要更新',
  collected_at       DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  play_url           MEDIUMTEXT      NOT NULL COMMENT '整串播放地址：第1集$http://...#第2集$http://...',
  created_at         DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at         DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
  PRIMARY KEY (id),
  UNIQUE KEY uk_vod_source_from (vod_id, source_id, source_from),
  KEY idx_source (source_id),
  KEY idx_source_vod_vod (source_id, source_vod_id, vod_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

改动与理由：

- **`source_id` 改可空**：手工添加的线路没有采集源。
- **不加 `play_line_id` 外键**：`lcm_play_line` 是「显示覆盖层」（改名、排序、停用），采集从不写它，前台用 `leftJoin` 按 `source_from` 关联，未注册的线路照样显示。加外键会让采集多一次 upsert，且线路注册后还要回填全量 `vod_play`。
- **`play_url` 不拆成「一集一行」**：十万影片 × 几十集会是数百万行，而解析只在请求单集播放时做一次。

⚠️ 注意：`source_id` 可空后，`uk_vod_source_from` 对 `NULL` 不去重（MySQL 唯一索引忽略 NULL）。手工添加的线路靠「同一 `vod_id` + `source_from`」在应用层保证唯一。

## 7. `lcm_collect_source_category` — 源站分类映射

```sql
CREATE TABLE lcm_collect_source_category (
  id                BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  source_id         BIGINT UNSIGNED NOT NULL DEFAULT 0,
  source_type_id    VARCHAR(50)     NOT NULL DEFAULT '' COMMENT '源站分类 id（字符串）',
  source_type_name  VARCHAR(100)    NOT NULL DEFAULT '' COMMENT '源站分类名快照，同步分类时刷新',
  source_type_pid   VARCHAR(50)     NOT NULL DEFAULT '' COMMENT '源站父分类 id，后台按两级树展示用',
  category_id       BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '映射到的本站分类，0 表示未映射',
  match_type        TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '映射方式：0 无 1 自动 2 手动（配合 status 区分手动映射 / 手动忽略）',
  status            TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0 未映射 1 已映射 2 已忽略',
  created_at        DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at        DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
  PRIMARY KEY (id),
  UNIQUE KEY uk_source_type (source_id, source_type_id),
  KEY idx_category (category_id),
  KEY idx_source_status (source_id, status),
  CONSTRAINT ck_status_mapped CHECK ((status = 1) = (category_id > 0))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

结论：字段全保留。`status` 看似能由 `category_id` + 忽略标记推导，但「已忽略」是独立状态，删了必须补一个布尔列，属于等价替换且会丢掉按状态筛选的索引，因此不删。

新增 CHECK 约束 `ck_status_mapped`，把「已映射」与「有目标分类」绑在一起：

```sql
CHECK ((status = 1) = (category_id > 0))
```

两边都挡：`status = 1` 但 `category_id = 0`（说映射了却没有目标）、`category_id > 0` 但 `status ≠ 1`（有目标却说未映射或已忽略）。`status = 2`（已忽略）的行必须为 `category_id = 0`。

现有库 196 行核对结果：156 行 `status = 1` 且 `category_id > 0`、40 行 `status = 2` 且 `category_id = 0`，违反 0 行，`category_id` 指向不存在分类的也 0 行。

```sql

```

改动与理由：

- **改名**：这张表是 `lcm_collect_task` 的执行记录，命名与 `lcm_collect_source` / `lcm_collect_source_category` 的父子结构保持一致。
- **新增 `task_name` 快照**：删除任务只删任务本身、记录保留（`apps/server/src/modules/collect-task/collect-task.service.ts`，不覆写删除），没有快照就只剩一个悬空 id。手动采集时写 `手动采集·<源站名>`。
- **`status` 与任务表同一套取值**（1 运行中 / 2 成功 / 3 失败 / 4 已取消），前端可共用一份映射。
- **新增 `idx_source_started`**：记录页支持按源站筛选，原来只有按任务、按时间的索引。
- `source_name` **不做**快照：源站名由列表接口现查（`apps/server/src/modules/collect-source/collect-source.service.ts` 的 `nameMap()`，按 `source_id IN (...)` 取 `id, name`）。删源站时 `CollectSourceService.purge()` 会在同一事务里把它的日志与日志明细一起删掉，所以不会留下空源站名的记录。
- **删源站连带删什么**（无物理外键，全由 `CollectSourceService.purge()` 在一个事务里按序做）：该源的分类映射、采集任务、采集记录与记录明细、替换规则、广告特征、播放地址；删完播放地址后一条线路都不剩的影片也一并删掉（否则前台点进去只会「还没有可播放的线路」）；`lcm_play_line` 里该源用过、且删后已无任何影片引用的线路注册行；`lcm_cover_check` 里已经没有封面引用的域名行。`lcm_vod_merge_ignore` 不动（键是哈希/`same:<id>-<name>`，删掉反而会让以后重新采集到同内容的影片又弹一次合并提醒）。删之前会先 `CollectRunner.cancelBySource()` 停掉该源正在跑的采集并等它收尾，避免删完又写回一条指向已删源的记录。
- 6 个计数器不合并：`total = inserted + updated + skipped + ignored + failed` 是记录详情的对账关系。

CREATE TABLE lcm_source_rule (

  source_id  BIGINT UNSIGNED NOT NULL DEFAULT 0,
  kind       TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '1 播放地址 2 图片地址',

  is_enabled TINYINT UNSIGNED NOT NULL DEFAULT 1,

## 17. `lcm_vod_merge_rule` — 入库合并规则

```sql
CREATE TABLE lcm_vod_merge_rule (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  rule_key    VARCHAR(32)     NOT NULL DEFAULT '' COMMENT '规则键：mode 或 lcm_vod 字段名',
  rule_value  VARCHAR(32)     NOT NULL DEFAULT '' COMMENT '策略标识，取值由 merge.ts 的白名单校验',
  created_at  DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at  DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),

  UNIQUE KEY uk_rule_key (rule_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='影片入库合并规则：每个字段一行';
```

改动与理由：

- **从 `lcm_setting.merge_rules` 的整份 JSON 改成一行一个字段**：JSON 解析失败只能整包回落默认值，也定位不到是哪一项坏了；拆成行后可以逐项校验、逐项更新，`GET/PUT /api/admin/vod-merge-rule` 直接按行读写。
- **字段元数据不进库**：中文名、可选策略、默认值仍由 `apps/server/src/modules/collect/merge.ts` 的 `MERGE_FIELDS` 定义，表里只存「这个键选了哪个策略」；因此新增可配置字段不需要迁移，前端也不再维护一份字段表。
- **`mode` 也占一行**（`rule_key = 'mode'`，值 `merge` / `off`），与各字段策略走同一套读写路径。
- 表为空时 `loadMergeConfig` 按默认值落库，并把旧的 `lcm_setting.merge_rules` 解析一次作为初始值；旧键之后不再读取（留在原处，可手工删除）。

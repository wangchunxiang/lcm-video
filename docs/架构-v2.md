## 1. 背景与目标

### 1.1 为什么要重构

当前代码**能跑、功能完整**，问题不在功能，在结构：

- 服务端没有任何强制分层，数据查询、业务规则、HTML 组装混在同一个 handler 里；
- 表结构定义了两遍（`init.sql` 与 `schema.ts`），且已经漂移；
- 前后台没有共享的数据契约，字段改名靠人工对齐；
- 前台模板（Liquid）无类型、无补全、无测试，且桌面/移动是两套平行的模板树。

### 1.2 目标（可验收）

1. **分层由框架强制**：`Controller` 只做参数与响应，`Service` 只做业务，`Prisma` 只做数据。控制器里出现 `prisma.` 视为违规。
2. **表结构单一真相源**：`schema.prisma` 一份定义，`prisma migrate` 管理变更，`init.sql` 退场。
3. **契约共享**：后台与前台使用同一份 DTO 类型，改字段时编译期报错。
4. **功能对齐**：后台现有功能点全部可用；前台现有页面与播放能力全部可用。**对齐的是功能，不是 HTML 或接口形状。**
5. **可灰度、可回滚**：新旧版本并行运行，按功能域切换，任一步都能在 10 分钟内退回旧版。
6. **部署不倒退**：仍是单进程 + PM2 + Dockerfile，只在构建链上增加编译步骤。

### 1.3 非目标（明确不做）

- 不改数据库产品（继续 MySQL 8）。
- 不改表的主键与字段语义；不删列（先标记废弃）。
- 不拆微服务、不引入消息队列；Redis 只在出现明确的缓存/会话需求时才评估。
- 不做多主题 / 多站点 / 白牌。
- 不做多语言。

### 1.4 这次是「重建」，不是「迁移」

v2.0 的思路是把现有代码翻译到新框架，靠「输出完全一致」来验收。**这个前提在 URL 可改、后台前端可换之后已经失效。** 新旧版本之间剩下的真正锚点只有两个：**数据**和**功能清单**。

| | 迁移（v1.0 思路） | 重建（v2.1 思路） |
|---|---|---|
| 验收基准 | 接口响应逐字段 diff、HTML 快照 diff | 功能清单逐条走查 + 写操作数据 diff |
| 旧代码定位 | 要翻译的资产 | **需求说明书 + 参照实现** |
| URL | 冻结 | 重新设计，旧 URL 301 |
| 后台前端 | 冻结 | 待定，可重写 |
| 上线方式 | 一次性合并 | 新旧并行，按域切换 |

这不代表旧代码没价值：采集（`lib/collect/*`）、广告清洗（`lib/ads/*`）、封面检测（`lib/covers/*`）、搜索的覆盖索引用法、列表页「父分类 OR 子分类拆两条查询」这些**实现智慧要照抄**。要重写的是骨架，不是算法。

## 2. 现状诊断

### 2.1 分层实况

```
apps/server/src/
├── index.ts            ← 组装一切：插件、路由、鉴权、调度、静态资源、异常处理
├── routes/             ← 22 个文件 / 99 个 handler / 183.6 KB
│   ├── site/           ← 前台页面，直接查库 + 直接渲染
│   └── admin/          ← 后台 API，直接查库 + 直接校验
├── lib/                ← 混杂：既有纯工具，也有业务（collect/、theme.ts）
└── env.ts
```

`lib/collect/` 是全项目唯一有分层的地方（`runner → parser → merge → writer`），重建时应**原样保留逻辑，只换外壳**。

### 2.2 七个具体问题

| 编号 | 问题 | 证据 |

| P1 | 路由即业务，单文件失控 | `routes/site/index.ts` 30.8 KB；`routes/admin/tools/merge.ts` 28.1 KB；`routes/admin/vods.ts` 21.1 KB |
| P2 | 表结构定义两遍且已漂移 | `packages/db/init.sql` 15 张表；`packages/db/src/schema.ts` 只有 14 个 `mysqlTable`——`lcm_vod_merge_ignore` 缺失，靠裸 SQL 访问：`apps/server/src/routes/admin/tools/merge.ts:56`、`:608`、`:611`、`:676` |

### 2.3 必须保留的资产

- **数据库设计**：`vod.cover_host` 生成列（域名统计走索引）、`idx_search` 覆盖索引（搜索不扫表）、`lcm_play_line` 线路注册表、多源合并判重逻辑。
- **采集逻辑**：`lib/collect/{runner,writer,merge,parser,client,classes,match}.ts` 与 3 个测试文件。
- **广告处理**：`lib/ads/{analyze,skip}.ts`；广告线路 m3u8 的 `/play/ad/*` 代理。
- **前台视觉与交互**：`themes/default/assets/{style.css,mobile.css,app.js,mobile.js}`、`docs/样式规范.md`、`docs/样式规范-移动端.md`。样式规范是设计资产，与模板引擎无关，重建时直接沿用。
- **后台前端**：`apps/admin` **作为功能参照与可复用实现**，不再是冻结资产。
- **部署约定**：单进程、`.env` 注入、`/uploads` 与 `/admin` 静态挂载。

### 2.4 功能基线（验收依据）

重建期不再以「输出一致」验收，改为以**功能清单**验收。两份清单正在产出：

- `docs/功能对齐-后端接口.md`：全量路由、入参、返回要点、权限、现有前台 URL 形态。
- `docs/功能对齐-后台页面.md`：15 个后台页面的功能点、依赖接口、Element Plus 组件用量、重写工作量估计。

**每个功能点需要标三档，由你确认：**

| 档位 | 含义 | 处理 |
|---|---|---|
| P0 | 必须保留，少一条就影响收入/运营 | 逐条验收，写进测试 |
| P1 | 应当保留，但交互/性能可以更好 | 可用新实现，验收时人工走查 |

## 3. 技术选型

### 3.1 总表

| 层 | 现状 | 目标 | 变化 |
|---|---|---|---|
| 运行时 | Node 24 + 原生类型剥离 | Node 24 + **编译产物**（Nest 需要反射元数据） | 改 |
| 服务端框架 | Fastify 5 | **NestJS 11**（Express 适配器） | 换 |
| 数据访问 | Drizzle 0.44 + mysql2 | **Prisma 6** | 换 |
| 表结构 | `init.sql` + `schema.ts` | **`schema.prisma`** + migrations | 换 |
| 校验 | 手写 | **class-validator / class-transformer** | 新增 |
| 前台渲染 | liquidjs | **待定**（D3，见 7.1） | 换 |
| 后台前端 | Vue 3 + Element Plus + Vite 6 | **待定**（D8，见 8.2） | 可能换 |
| 共享层 | 纯函数 | 纯函数 + DTO 类型 | 扩 |
| 测试 | vitest（纯函数） | vitest + Nest Testing（路由级 + DB 级） | 扩 |
| 日志 | pino（Fastify 内置） | nestjs-pino（仍是 pino） | 换壳 |
| 部署 | PM2 + Dockerfile（跑 `src/index.ts`） | PM2 + Dockerfile（跑 `dist/main.js`） | 改一行 |

### 3.2 为什么是 NestJS

**它提供 Spring Boot 那套骨架**：模块、控制器、服务、依赖注入、管道校验、守卫、异常过滤器、拦截器。项目现有的语法、命名和层次期望可以被框架直接满足，而不是靠自觉。

**必须接受的代价（写在前面）：**

1. **不能再直接 `node src/index.ts`**。装饰器不是可擦除语法，`erasableSyntaxOnly` 必须移除，`experimentalDecorators` + `emitDecoratorMetadata` 必须开启，产物进入 `dist/`。
2. **不要用 esbuild/tsx 跑 Nest**。esbuild 不实现 `emitDecoratorMetadata`，依赖注入会解析不到构造参数类型。用 `nest build`（tsc）或 `@swc/core`。
3. **文件数膨胀**：22 个路由文件 → 预计 50~70 个文件。
4. **前台 SSR 不是一等公民**，需要自定义渲染（见 7.1）。

### 3.3 为什么是 Prisma

对照 MyBatis-Plus 的体验：

| MyBatis-Plus | Prisma |
|---|---|
| `BaseMapper<T>` 自动 CRUD | `prisma.vod.findMany()` / `createMany()` |
| `QueryWrapper` | `where: { year: { gte: 2000 } }` |
| 分页插件 | `skip` / `take` + `count()` |
| 逻辑删除、自动填充 | `@default(now())` + 中间件 |
| Flyway / Liquibase | `prisma migrate dev` / `migrate deploy` |
| 手写 join 的 XML | `$queryRaw` 兜底 |

**收益**：一份 schema 管表结构与迁移，彻底解决 P2/P3；生成的客户端自带类型，字段改名即编译报错。

**代价（同样写在前面）：**

- Docker 构建与部署多一步 `prisma generate`；
- **生成列不受支持**：`vod.cover_host` 在 Prisma 里无法建模，只能 `@ignore` 并在需要时用 `$queryRaw`（影响 `lib/covers/check.ts` 与后台的域名统计）；
- 复杂聚合与多表统计更适合 `$queryRaw`，Prisma 的 `groupBy` 能力有限。

### 3.4 已否决

| 选项 | 否决理由 |
|---|---|
| 继续 Fastify + 自建分层 | 分层靠自觉，正是当前的病根 |
| Hono + 自建分层 | 同上，且要的是"框架强制结构" |
| Express 5 | 类型与生态均不如前后两者 |
| Elysia / Nest+Hono 混搭 | 绑定 Bun，或与主进程模式冲突 |
| Kysely | 更贴合 MyBatis 习惯，但迁移管理要另配一套，收益不抵成本（可随时复议） |
| TypeORM / Sequelize / MikroORM | 装饰器与元数据包袱更重，生态活跃度不如 Prisma |
| tsx / esbuild 跑 Nest | `emitDecoratorMetadata` 缺失，注入不可靠 |
| Nuxt / Astro / Next | 会接管路由或构建，与 NestJS 冲突 |

## 4. 目标架构

### 4.1 进程与部署

保持单进程：`dist/main.js` 由 PM2 fork 模式守护，Docker 镜像内 `npm ci → prisma generate → nest build → npm run build (admin)`。

```
浏览器 ──┬─> /                前台 SSR（NestJS 控制器直出 HTML）
         ├─> /api/play/...     前台轻量接口（换集用）
         ├─> /api/admin/*      后台 API（JWT 守卫）
         ├─> /admin/*          后台 SPA 静态文件
         ├─> /uploads/*        上传文件静态服务
         └─> /healthz          健康检查
```

采集调度器仍在进程内（D6），启动时接管中断任务的行为保持不变。

### 4.2 分层与依赖方向

```
        ┌──────────────────────────────────────────┐
        │  Controller  参数解析 / 校验 / 响应       │  不许出现 prisma.
        ├──────────────────────────────────────────┤
        │  Service     业务规则 / 事务 / 组装       │  不许出现 Request/Response
        ├──────────────────────────────────────────┤
        │  PrismaService / RawQuery                 │  只做数据访问
        └──────────────────────────────────────────┘
```

三条硬规则：

1. **控制器不许注入 `PrismaService`**，只能注入 Service。
2. **Service 不许依赖 Nest 的 HTTP 对象**（`@Req`/`@Res`/`Response`），保证可单测。
3. **跨模块调用只走对方导出的 Service**，不许直接 import 别人的 Prisma 查询。

### 4.3 仓库结构

```
apps/
├── server/                          # NestJS：API + 前台 SSR 渲染（同进程）
│   ├── src/
│   │   ├── main.ts                  # 引导：全局管道/过滤器/拦截器、静态、视图
│   │   ├── app.module.ts
│   │   ├── config/                  # 配置装载与校验（原 env.ts）
│   │   ├── common/
│   │   │   ├── filters/api-exception.filter.ts
│   │   │   ├── interceptors/response.interceptor.ts
│   │   │   ├── interceptors/date-format.interceptor.ts
│   │   │   ├── decorators/public.decorator.ts
│   │   │   └── dto/pagination.dto.ts
│   │   ├── prisma/                  # PrismaService（全局模块）
│   │   ├── modules/
│   │   │   ├── site/                # 前台：控制器 + pages + components + 路由表
│   │   │   ├── admin/               # 后台：auth/vods/categories/lines/settings/
│   │   │   │                        #       sources/tasks/logs/tools/dashboard/upload
│   │   │   └── collect/             # 采集：scheduler/runner/parser/merge/writer/client
│   │   └── assets/                  # 原 themes/default/assets（css/js/vendor）
│   ├── prisma/
```

若 D3 选 Vue SSR / React SSR，前台视图层拆成独立包更干净：`packages/site-views`（组件与构建），`apps/server` 只负责取数与调用渲染函数。**不要**拆成独立部署的站点应用——那会多一跳 HTTP 和一套鉴权。

### 4.5 横切关注点

| 关注点 | 实现 | 替代的现状 |
|---|---|---|
| 响应信封 | `ResponseInterceptor` 或各控制器显式返回 + 统一包装 | `lib/http.ts` 的 `ok/fail`（同时收编 `/api/play/*` 的 `{ok:true}`） |
| 异常→信封 | `ApiExceptionFilter`（全局） | `index.ts` 的 `setErrorHandler` |
| 404 | `ErrorController` + `@Catch` | `setNotFoundHandler` |
| 鉴权 | `JwtAuthGuard` + `@Public()` | `lib/auth-guard.ts` 的 `preHandler` |
| 校验 | 全局 `ValidationPipe`（whitelist + transform） | 手写 `toInt` / `toText` |
| Date 序列化 | `DateFormatInterceptor`（等价行为） | 全局 `preSerialization` |
| 压缩 | `compression` 中间件 | `@fastify/compress` |
| Cookie / multipart | `cookie-parser` / `multer` | `@fastify/cookie` / `@fastify/multipart` |
| 安全响应头 | 全局中间件 | `onSend` 钩子 |
| 日志 | `nestjs-pino` | Fastify 内置 pino |
| 配置 | `ConfigModule` + 启动期校验 | `env.ts` |
| 健康检查 | 保留 `/healthz` | 现有实现 |
| 旧 URL 301 | 全局中间件 + 映射表 | 无（新需求） |

### 4.6 数据访问规范

1. 简单查询用 Prisma Client；多表统计、生成列、批量 upsert 用 `$queryRaw`，集中在 `*.raw.ts` 文件里，**不许散落在 Service 中**。
2. 事务统一走 `prisma.$transaction`，Service 内完成，不跨控制器。
3. 所有返回给外部的数据必须经过 `toDto()` 映射，**禁止直接把 Prisma 模型返回给前端**（避免 `cover_host` 之类的内部字段泄漏、`Date` 类型外泄）。

### 5.3 baseline 迁移

4. `prisma migrate resolve --applied <baseline>` 在现有库上标记为已应用；
5. 此后所有变更走 `prisma migrate dev`（本地）与 `migrate deploy`（生产）。

### 5.4 保留的 MySQL 特性

- 字符集 `utf8mb4` / `utf8mb4_unicode_ci`；
- 索引原样保留（含 `idx_search` 覆盖索引）；
- `vod.cover_host` 生成列与 `idx_cover_host` 保留在库侧，Prisma 侧 `@ignore`，读写走 `$queryRaw`；
- 连接串：`DATABASE_URL="mysql://user:pass@host:port/db"`，由现有 `DB_*` 环境变量拼装，保留在 `.env`。

### 5.5 数据库变更策略（D10）

「尽量不动」要落成可执行的规则，否则 Phase 2 之后每次 `migrate dev` 都可能生成意外 DDL。

| 变更类型 | 结论 | 备注 |
|---|---|---|
| 新增表 | ✅ 允许 | 全部走 `migrate dev`，进 git |
| 新增可空列 / 带默认值列 | ✅ 允许 | 大表加列避开高峰 |
| 新增索引 | ✅ 允许 | 先评估写入放大 |
| 修改列类型 / 长度 | ⚠️ 需评估 | 先 `SHOW CREATE TABLE` 对比，必要时停写入窗口 |
| 新增唯一约束 | ⚠️ 需评估 | 先跑重复值检测 SQL |
| 改主键 / 改字段语义 | ❌ 禁止 | 宁可新增列 + 双写 |
| 删除列 / 删除表 | ❌ 禁止 | 先标记废弃，稳定一版后再删 |

**baseline 必须逐表对齐。** Phase 2 验收要求：对 15 张表执行 `SHOW CREATE TABLE`，与 `init.sql` 的建表语句逐字符对比（允许等价写法差异，逐条记录）。否则以后 `migrate dev` 会把「你以为没变」的差异当成 DDL 再执行一遍。

**新功能可能想动库的地方**（本次不承诺，出现时按上表评估）：

- 用户体系：`lcm_user`、`lcm_user_favorite`、`lcm_play_history`；
- 播放统计：按日聚合表；
- 采集增强：源站健康状态、任务重试计数。

## 7. 前台方案

### 7.1 渲染层决策（D3）

三个候选，**共同前提**：内容站的首屏是 HTML，客户端 JS 只负责换集、抽屉、筛选这类局部交互，不做客户端路由。

| | A. TS 服务端组件 | B. Vue SSR | C. React SSR |
|---|---|---|---|
| 形态 | `(props) => string` 纯函数组件 | `renderToString(createSSRApp(...))` | `renderToPipeableStream` |
| 构建 | 无（仅 tsc） | Vite 产 SSR bundle + 客户端 bundle | 同 Vue，另需 CSS-in-JS 提取 |
| 类型安全 | 强（props 有类型） | 强（SFC + defineProps） | 强 |
| 组件复用 | 自建（卡片、行、分页手写） | 生态丰富，可复用后台组件风格 | 生态丰富 |
| 交互升级路径 | 原生 JS（现有 `app.js` 模式） | 平滑（同一套组件补 hydrate） | 同 |
| 运维复杂度 | 低 | 中（两套产物、sourcemap、缓存） | 中高（CSS-in-JS SSR 额外处理） |
| 与后台关系 | 无关 | 若后台也是 Vue → 一套心智 | 若后台也是 React → 一套心智 |

**我的建议：A（TS 服务端组件），除非你明确想要"前台也用组件化开发体验"。**

理由：

1. 站点是内容型页面，客户端几乎不需要状态；hydration 带来的构建链与首批 JS 体积，换不来对应收益。
2. 现有 `app.js` / `mobile.js` 已经把换集、抽屉、筛选做完了，这套模式在 A 下原样保留。
3. 后台若保留 Vue，B 的"统一"收益只体现在"同一套框架心智"上，代码并不复用（后台是表格表单，前台是卡片列表）。
4. 未来若真要做用户中心/收藏/历史，那是**独立的客户端应用**（或局部 island），不必让整站变成 SPA 架构。

**反对意见也要记下来**：如果你更看重 DX（SFC、热更新、组件生态）而不是运维简单，B 是合理的，代价是构建链复杂一档。这不是对错问题，是取舍。

**不选模板引擎（Handlebars/EJS）**：那只是把 Liquid 换成另一种无类型检查的模板，P6 的问题原封不动。

### 7.2 路由规范（D9 草案）

**现状**

| 路径 | 说明 |
|---|---|
| `/` | 首页 |
| `/today` | 今日更新 |
| `/list/:alias?type=&year=&sort=&page=` | 分类列表；`type` 为子分类 alias，`sort` 为 `time`（默认）/`new` |
| `/detail/:id` | 详情 |
| `/play/:id/:playId/:ep` | 播放；`playId` 实为线路 id，`ep` 为 1 基集数 |
| `/search?wd=&year=&sort=&page=` | 搜索 |
| `/api/play/:id/:playId/:ep` | 换集 JSON |
| `/play/ad/:id/:playId/:ep` | 广告线路 m3u8 代理 |

**新规范（草案）**

| 新路径 | 说明 | 旧路径 | 迁移方式 |
|---|---|---|---|
| `/` | 首页 | `/` | 不变 |
| `/today` | 今日更新 | `/today` | 不变 |
| `/category/:alias` | 分类列表 | `/list/:alias` | 301 |
| `/category/:alias?type=&year=&sort=&page=` | 筛选/分页 | 同左 | 参数名保持不变 |
| `/vod/:id` | 详情 | `/detail/:id` | 301 |
| `/play/:id/:line/:ep` | 播放 | `/play/:id/:playId/:ep` | 301，`:line` 仍是线路 id |
| `/search?wd=` | 搜索 | `/search?wd=` | 不变 |
| `/api/v1/play/:id/:line/:ep` | 换集 JSON | `/api/play/...` | 旧路径保留一版 |
| `/play/ad/:id/:line/:ep` | 广告代理 | 同左 | 不变 |

**五条原则**

1. **路径表达资源，查询参数表达筛选与分页。** 现状已经是这样，保持，不要引入 `/list/1-2-3.html` 这类魔数路径。
2. **不用文件扩展名，不用 `?id=`。** 详情页用路径段，利于 canonical 与分享。
3. **分类用 alias，影片用 id。** alias 可读、稳定；影片名会变，用 id。
4. **`/api/*` 加版本前缀。** 换集接口未来改字段时，旧前端还能活一版。
5. **一个资源只有一种规范 URL**，其余形式一律 301 到规范 URL（含分页第 1 页、默认排序）。

**同时要定的两件事**

- **canonical**：列表页带筛选参数时，canonical 指向哪里？现状是 `/list/:alias`（丢掉筛选）。建议保持——筛选页不索引，避免重复内容。
- **sitemap / robots（D12）**：当前项目**没有** sitemap.xml 与 robots.txt（已确认代码里不存在）。换 URL 恰好是补上的时机，但也意味着这是一项新增工作量，要单独决定做不做。

### 7.3 页面数据契约（示例）

```ts
// packages/shared/src/dto/site.ts
export interface VodCard {
  id: number;
  name: string;
  cover: string;
  remarks: string;
  year: number;
  categoryAlias: string;
}

export interface HomePageData {
  site: SiteInfo;
  nav: NavItem[];
  banner: VodCard[];
  rows: Array<{ title: string; alias: string; items: VodCard[] }>;
}
```

约束：`PageData` 里不许出现 `Date`、`Buffer` 或 Prisma 生成的类型；时间统一为已格式化的字符串。

### 7.4 静态资源

- CSS/JS 从 `apps/server/src/assets` 由静态中间件直出，加长缓存 + 版本号 query（沿用现有 `asset` filter 的 `?v=` 语义）；
- `uploads/` 映射到 `/uploads/`（30 天缓存，行为不变）；
- 桌面与移动**共用一套组件与一套 CSS**，用断点与 `variant` 表达差异，不再维护两套模板树（`docs/样式规范-移动端.md` 的间距/触控规则转为 CSS 变量与媒体查询）。

### 7.5 SEO 不可回退清单

- title / description / canonical、OG 标签、面包屑 JSON-LD；
- 404 返回真实 404 状态码；
- 页面 HTML 完全直出（禁用 JS 也可读）；
- 列表页筛选参数不进入 canonical；
- 播放页不索引（`noindex`，与现状一致）。

### 7.6 旧 URL 与 SEO 迁移

换 URL 是本次唯一可能直接影响流量的动作，必须当发布来处理：

1. **301 映射表**：在 Nest 里做一层全局中间件，读到旧路径直接 301，不进控制器。映射表写成常量文件，附单元测试（旧路径→新路径全覆盖）。
2. **保留期**：至少 6 个月，建议 12 个月。日志里统计 301 命中，降到阈值以下再摘。
3. **灰度期加 `noindex`**：v2 在临时域名/IP 上试运行时不希望被索引，用环境变量控制。
4. **提交**：上线当天提交新 sitemap（若 D12 决定做）、在搜索资源平台提交改版规则。
5. **不要做的事**：不要同时改 URL 又改标题模板又改页面结构。一次只改一层，出问题才能定位。

## 8. 后台方案

### 8.1 功能对齐

- 15 个页面、功能点清单见 `docs/功能对齐-后台页面.md`；
- 对齐的判据是「同一件事能以不更差的方式完成」：字段能改、筛选能筛、批量能批、导入导出结果一致、长任务有进度；
- **不要求**像素一致、组件一致、请求路径一致。

### 8.2 前端决策（D8）

**这不是一个独立决策，它是 D3 的从属决策。** 决策顺序反了会白做功：

```
前台渲染层（D3）
├─ A. TS 服务端组件 ──> 后台：保留 Vue 3 + EP（推荐）
├─ B. Vue SSR       ──> 后台：保留 Vue 3 + EP（顺理成章）
└─ C. React SSR     ──> 后台：才值得迁 React + Antd
```

理由：

1. 后台 90% 是表格 + 表单 + 弹窗，现有 `apps/admin` 已经把这些模式跑通（`el-table` 插槽、分页、二次确认、上传、动态表单）。**重写它换来的只是"框架统一"，而框架统一本身不产生业务价值。**
2. 真正需要前后台共享的只有 **DTO 类型**，放在 `packages/shared`，与框架无关。
3. 只有当前台也选 React 时，"统一"才等于"组件/工具函数/构建配置都能共用"，迁移才有净收益。
4. 成本参考：15 个页面 + `VodEditDialog`（20 KB）约 2.3 万行 Vue。按经验，重写 + 回归不低于 4~6 周，且期间两套后台并存，出错概率不低。

**如果坚持换 React**，建议这样做：先只重写「影视管理 + 采集源站 + 采集任务」这三个最复杂的页面，验证 Antd 能否覆盖 EP 的表格/表单能力；跑顺了再批量迁，不要一次性推倒。

### 8.3 若保留 Vue：做结构性重构（推荐）

不做推倒重写，但把这次暴露的问题一并解决：

1. **请求层收口**：现在每个页面自己 `fetch` + 自己声明类型 → 换成 `src/api/*.ts`，返回类型来自 `@lcm/shared` 的 DTO。
2. **抽公共表格组件**：`<DataTable>` 封装分页、加载态、空态、错误重试、列配置，15 个页面里至少 10 个能直接用。
3. **抽公共表单弹窗**：`<FormDialog>` 统一提交/校验/关闭行为。
4. **删掉占位页与死代码**：`Placeholder.vue` 与菜单里未实现的入口。
5. **构建与类型分开**：`vue-tsc` 进 `npm run check`，现在后台的类型错误只靠编辑器发现。

### 8.4 若改 React：代价与风险

| 项 | 说明 |
|---|---|
| 工作量 | 4~6 周（含回归），期间功能冻结风险高 |
| 组件覆盖 | Antd 的 Table/Form 能力不弱于 EP，但 `el-table` 的 `scoped-slot` 写法要整体改写，机械劳动多 |
| 样式 | EP 走 CSS 文件，Antd 5 走 CSS-in-JS；若前台也做 SSR，需要 `@ant-design/cssinjs` 的样式提取 |
| 团队 | 单人长期维护时，两套心智（Vue 旧代码 / React 新代码）在过渡期是负担 |
| 收益 | 只有"与前台统一"这一条，前提是前台也选 React |

## 9. 迁移与切换（D11）

### 9.1 并行部署

```
                  ┌──────────────────────────────┐
  用户 ──DNS/反代──>│ v1  apps/server (Fastify)     │──┐
                  └──────────────────────────────┘  │
                  ┌──────────────────────────────┐  ├──> 同一个 MySQL
  内测/灰度 ──────>│ v2  apps/server (NestJS)      │──┘
                  └──────────────────────────────┘
```

- v1 继续在 `master` 分支服务线上；
- v2 在 `v2` 分支，部署到独立端口（或临时子域），连同一个库；
- 两套代码**不共享写入口**：采集调度只在一边跑（默认 v1，直到 v2 Phase 5 验收）；
- v2 后台先以只读方式验证数据读取，写操作等 Phase 3 验收后再接管。

### 9.2 单一写入口原则

同一时刻，同一类写操作只能有一个版本在跑：

| 写操作 | 切换时机 |
|---|---|
| 采集入库 | Phase 5 验收后，停 v1 调度，启 v2 调度 |
| 后台增删改 | Phase 3 验收后，后台入口切到 v2，v1 后台下线 |
| 上传 | 跟随后台切换 |
| 用户前台交互（无写入） | 无需协调 |

这条原则比"功能齐了再切"更重要——两套采集同时跑会造成重复入库，且很难事后清理。

### 9.3 阶段

| 阶段 | 内容 | 验收 | 预估 |
|---|---|---|---|
| Phase 0 | 功能基线：两份清单 + P0/P1/P2 标注 + 关键写操作样本数据 | 清单评审通过，P2 项经你确认 | 1~2 天 |
| Phase 1 | Nest 骨架：`/healthz`、静态、404、异常信封、`PrismaService` | `dist/main.js` 可被 PM2/Docker 启动；旧站点不受影响 | 1~2 天 |
| Phase 2 | 数据层：baseline 迁移 + 15 表 `SHOW CREATE TABLE` 逐表对齐 | 空库可建、现库 `migrate status` 同步、逐表 diff 通过 | 1~2 天 |
| Phase 3 | 后台 API + 后台前端（D8） | 功能清单 P0 全过；关键写操作前后数据 diff 一致 | 5~8 天 |
| Phase 4 | 前台页面（D3）+ 新 URL + 301 中间件 | 7 类页面可用；301 覆盖测试全过；SEO 元素齐全 | 5~7 天 |
| Phase 5 | 采集与广告迁移 | 一次完整采集成功率/耗时相对基线无退化；中断恢复一致 | 2 天 |
| Phase 6 | 灰度切换 | 灰度 3~7 天无 5xx 抬升；301 命中正常；搜索收录无断崖 | 3~7 天 |
| Phase 7 | 收尾：删 Fastify/Drizzle/liquidjs/`themes/`，合并桌面前台 CSS | `npm run check` 全绿；镜像体积不增；TTFB 不高于基线 | 1~2 天 |

### 9.4 回滚

- 每一阶段结束打 tag（`v2-phase3` 等）；
- 反代/DNS 切回 v1 即可回滚前台，10 分钟内；
- 数据层回滚靠迁移文件的可逆性（DDL 只做加法时天然可回滚）；
- 301 中间件可单独开关（环境变量），出问题先关它。

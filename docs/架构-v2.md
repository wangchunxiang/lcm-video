## 1. 背景与目标

### 1.1 为什么要重构

当前代码**能跑、功能完整**，问题不在功能，在结构：

- 服务端没有任何强制分层，数据查询、业务规则、HTML 组装混在同一个 handler 里；
- 表结构定义了两遍（`init.sql` 与 `schema.ts`），且已经漂移；
- 前后台没有共享的数据契约，字段改名靠人工对齐；
- 前台模板（Liquid）无类型、无补全、无测试，且桌面/移动是两套平行的模板树。

### 1.2 目标（可验收）

1. **分层由框架强制**：`Controller` 只做参数与响应，`Service` 只做业务，`Prisma` 只做数据。控制器里出现 `prisma.` 视为违规。
2. **表结构单一真相源**：`schema.prisma` 一份定义，`prisma migrate` 一条命令建表/升级，`init.sql` 退场。
3. **契约共享**：后台与前台使用同一份 DTO 类型，改字段时编译期报错。
4. **URL 不变**：前台 7 个页面的路径、后台所有 `/api/admin/*` 路径与响应结构保持完全一致。
5. **可回归**：每阶段都有可执行的验收清单（见第 8 章），任何阶段可单独回滚。
6. **部署不倒退**：仍是单进程 + PM2 + Dockerfile，只在构建链上增加编译步骤。

### 1.3 非目标（明确不做）

- 不改数据库产品（继续 MySQL 8）。
- 不改表的主键、字段语义与索引设计。
- 不改后台前端技术栈与构建方式。
- 不拆微服务、不引入消息队列、不改单机部署形态。
- 不做多主题 / 多站点 / 白牌。
- 不在本次引入 Redis、全文检索引擎或对象存储。

## 2. 现状诊断

### 2.1 分层实况

```
apps/server/src/
├── index.ts            ← 组装一切：插件、路由、鉴权、调度、静态资源、异常处理
├── routes/             ← 22 个文件 / 99 个 handler / 183.6 KB
│   ├── site/           ← 前台页面，直接查库 + 直接渲染
│   └── admin/          ← 后台 API，直接查库 + 直接校验
├── lib/                ← 混杂：既有纯工具，也有业务（collect/、theme.ts）
└── env.ts
```

`lib/collect/` 是全项目唯一有分层的地方（`runner → parser → merge → writer`），迁移时应**原样保留逻辑，只换外壳**。

### 2.2 七个具体问题

| 编号 | 问题 | 证据 |
|---|---|---|
| P1 | 路由即业务，单文件失控 | `routes/site/index.ts` 30.8 KB；`routes/admin/tools/merge.ts` 28.1 KB；`routes/admin/vods.ts` 21.1 KB |
| P2 | 表结构定义两遍且已漂移 | `packages/db/init.sql` 15 张表；`packages/db/src/schema.ts` 只有 14 个 `mysqlTable`——`lcm_vod_merge_ignore` 缺失，靠裸 SQL 访问：`apps/server/src/routes/admin/tools/merge.ts:56`、`:608`、`:611`、`:676` |
| P3 | 迁移无版本化 | `packages/db/migrations/` 不存在；`db:init` 只是把 `init.sql` 整段灌库 |
| P4 | 无共享契约 | `packages/shared` 只有纯函数；admin 各页面自行声明接口类型 |
| P5 | 校验靠手写 | `routes/admin/vods.ts` 的 `VodBody` 全 `unknown` + `toInt`/`toText` + `LIMITS` 映射表 |
| P6 | 前台模板双轨 | 23 个 `.liquid`，其中 7 个页面模板桌面/移动各一份 |
| P7 | 测试缺失 | 6 个测试文件，全部是纯函数；无路由级、无 DB 级 |

### 2.3 必须保留的资产

- **数据库设计**：`vod.cover_host` 生成列（域名统计走索引）、`idx_search` 覆盖索引（搜索不出索引）、`lcm_play_line` 线路注册表、多源合并判重逻辑。
- **采集逻辑**：`lib/collect/{runner,writer,merge,parser,client,classes,match}.ts` 与 3 个测试文件。
- **广告处理**：`lib/ads/{analyze,skip}.ts`。
- **前台视觉与交互**：`themes/default/assets/{style.css,mobile.css,app.js,mobile.js}`、`docs/样式规范.md`、`docs/样式规范-移动端.md`。
- **后台前端**：`apps/admin` 全部。
- **部署约定**：单进程、`.env` 注入、`/uploads` 与 `/admin` 静态挂载。

## 3. 技术选型

### 3.1 总表

| 层 | 现状 | 目标 | 变化 |
|---|---|---|---|
| 运行时 | Node 24 + 原生类型剥离 | Node 24 + **编译产物**（Nest 需要反射元数据） | 改 |
| 服务端框架 | Fastify 5 | **NestJS 11**（Express 适配器） | 换 |
| 数据访问 | Drizzle 0.44 + mysql2 | **Prisma 6** | 换 |
| 表结构 | `init.sql` + `schema.ts` | **`schema.prisma`** + migrations | 换 |
| 校验 | 手写 | **class-validator / class-transformer** | 新增 |
| 前台渲染 | liquidjs | **TS 服务端组件**（D3） | 换 |
| 后台前端 | Vue 3 + Element Plus + Vite 6 | 不变 | — |
| 共享层 | 纯函数 | 纯函数 + DTO 类型 | 扩 |
| 测试 | vitest（纯函数） | vitest + Nest Testing（路由级） | 扩 |
| 日志 | pino（Fastify 内置） | nestjs-pino（仍是 pino） | 换壳 |
| 部署 | PM2 + Dockerfile（跑 `src/index.ts`） | PM2 + Dockerfile（跑 `dist/main.js`） | 改一行 |

### 3.2 为什么是 NestJS

**它提供 Spring Boot 那套骨架**：模块、控制器、服务、依赖注入、管道校验、守卫、异常过滤器、拦截器。项目现有的语法、命名和层次期望可以被框架直接满足，而不是靠自觉。

**必须接受的代价（写在前面）：**

1. **不能再直接 `node src/index.ts`**。装饰器不是可擦除语法，`erasableSyntaxOnly` 必须移除，`experimentalDecorators` + `emitDecoratorMetadata` 必须开启，产物进入 `dist/`。
2. **不要用 esbuild/tsx 跑 Nest**。esbuild 不实现 `emitDecoratorMetadata`，依赖注入会解析不到构造参数类型。用 `nest build`（tsc）或 `@swc/core`。
3. **文件数膨胀**：22 个路由文件 → 预计 50~70 个文件。
4. **前台 SSR 不是一等公民**，需要自定义渲染（见 7.1）。

### 3.3 为什么是 Prisma

对照 MyBatis-Plus 的体验：

| MyBatis-Plus | Prisma |
|---|---|
| `BaseMapper<T>` 自动 CRUD | `prisma.vod.findMany()` / `createMany()` |
| `QueryWrapper` | `where: { year: { gte: 2000 } }` |
| 分页插件 | `skip` / `take` + `count()` |
| 逻辑删除、自动填充 | `@default(now())` + 中间件 |
| Flyway / Liquibase | `prisma migrate dev` / `migrate deploy` |
| 手写 join 的 XML | `$queryRaw` 兜底 |

**收益**：一份 schema 管表结构与迁移，彻底解决 P2/P3；生成的客户端自带类型，字段改名即编译报错。

**代价（同样写在前面）：**

- Docker 构建与部署多一步 `prisma generate`；
- **生成列不受支持**：`vod.cover_host` 在 Prisma 里无法建模，只能 `@ignore` 并在需要时用 `$queryRaw`（影响 `lib/covers/check.ts` 与后台的域名统计）；
- 复杂聚合与多表统计更适合 `$queryRaw`，Prisma 的 `groupBy` 能力有限。

### 3.4 已否决

| 选项 | 否决理由 |
|---|---|
| 继续 Fastify + 自建分层 | 分层靠自觉，正是当前的病根 |
| Hono + 自建分层 | 同上，且你要的是"框架强制结构" |
| Express 5 | 类型与生态均不如前后两者 |
| Nested/Hono 混搭、Elysia | 绑定 Bun，或与主进程模式冲突 |
| Kysely | 更贴合 MyBatis 习惯，但迁移管理要另配一套，收益不抵成本（可随时复议） |
| TypeORM / Sequelize / MikroORM | 装饰器与元数据包袱更重，生态活跃度不如 Prisma |
| tsx / esbuild 跑 Nest | `emitDecoratorMetadata` 缺失，注入不可靠 |
| Nuxt / Astro / Next | 会接管路由或构建，与 NestJS 冲突 |

## 4. 目标架构

### 4.1 进程与部署

保持单进程：`dist/main.js` 由 PM2 fork 模式守护，Docker 镜像内 `npm ci → prisma generate → nest build → npm run build (admin)`。

```
浏览器 ──┬─> /                前台 SSR（NestJS 控制器直出 HTML）
         ├─> /api/play/...     前台轻量接口（换集用）
         ├─> /api/admin/*      后台 API（JWT 守卫）
         ├─> /admin/*          后台 SPA 静态文件
         ├─> /uploads/*        上传文件静态服务
         └─> /healthz          健康检查
```

采集调度器仍在进程内（D6），启动时接管中断任务的行为保持不变。

### 4.2 分层与依赖方向

```
        ┌──────────────────────────────────────────┐
        │  Controller  参数解析 / 校验 / 响应       │  不许出现 prisma.
        ├──────────────────────────────────────────┤
        │  Service     业务规则 / 事务 / 组装       │  不许出现 Request/Response
        ├──────────────────────────────────────────┤
        │  PrismaService / RawQuery                 │  只做数据访问
        └──────────────────────────────────────────┘
```

三条硬规则：

1. **控制器不许注入 `PrismaService`**，只能注入 Service。
2. **Service 不许依赖 Nest 的 HTTP 对象**（`@Req`/`@Res`/`Response`），保证可单测。
3. **跨模块调用只走对方导出的 Service**，不许直接 import 别人的 Prisma 查询。

### 4.3 仓库结构

```
apps/
├── server/                          # 改造为 NestJS
│   ├── src/
│   │   ├── main.ts                  # 引导：全局管道/过滤器/拦截器、静态、视图
│   │   ├── app.module.ts
│   │   ├── config/                  # 配置装载与校验（原 env.ts）
│   │   ├── common/
```

### 4.5 横切关注点

| 关注点 | 实现 | 替代的现状 |
|---|---|---|
| 响应信封 | `ResponseInterceptor` 或各控制器显式返回 + 统一包装 | `lib/http.ts` 的 `ok/fail` |

| 404 | `ErrorController` + `@Catch` | `setNotFoundHandler` |

| 校验 | 全局 `ValidationPipe`（whitelist + transform） | 手写 `toInt` / `toText` |

| 健康检查 | `@nestjs/terminus` 或保留 `/healthz` | 现有实现 |

### 4.6 数据访问规范

1. 简单查询用 Prisma Client；多表统计、生成列、批量 upsert 用 `$queryRaw`，集中在 `*.raw.ts` 文件里，**不许散落在 Service 中**。
2. 事务统一走 `prisma.$transaction`，Service 内完成，不跨控制器。
3. 所有返回给外部的数据必须经过 `toDto()` 映射，**禁止直接把 Prisma 模型返回给前端**（避免 `cover_host` 之类的内部字段泄漏、`Date` 类型外泄）。

### 5.3 baseline 迁移

生产库已有数据，不能期望 Prisma 从零建表。流程：

1. `prisma db pull` 从现有库反向生成 `schema.prisma` 初稿；
2. 人工校正字段类型、`@ignore` 生成列、补齐 `lcm_vod_merge_ignore`；
3. `prisma migrate diff --from-empty --to-schema-datamodel` 生成基线 SQL；
4. `prisma migrate resolve --applied <baseline>` 在现有库上标记为已应用；
5. 此后所有变更走 `prisma migrate dev`（本地）与 `migrate deploy`（生产）。

### 5.4 保留的 MySQL 特性

- 字符集 `utf8mb4` / `utf8mb4_unicode_ci`；
- 索引原样保留（含 `idx_search` 覆盖索引）；
- `vod.cover_host` 生成列与 `idx_cover_host` 保留在库侧，Prisma 侧 `@ignore`，读写走 `$queryRaw`；
- 连接串：`DATABASE_URL="mysql://user:pass@host:port/db"`，由现有 `DB_*` 环境变量拼装，保留在 `.env`。

## 6. API 契约

### 6.1 响应信封（不变）

```json
{ "code": 0, "msg": "ok", "data": {} }
```

### 6.2 错误码（不变）

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 40000 | 参数错误 |
| 40100 | 未登录 / 凭证失效 |
| 40300 | 无权限 |
| 40400 | 不存在 |
| 50000 | 服务端错误 |

### 6.3 分页约定

统一为 `{ items: T[], total: number, page: number, pageSize: number }`，在 `packages/shared/src/dto/pagination.ts` 定义 `Paged<T>`，后台所有列表接口复用。

### 6.4 DTO 归属

- `packages/shared/src/dto/`：仅类型与纯函数（无装饰器、无框架依赖），供 admin 与 server 共用；
- `apps/server/src/modules/**/dto/`：含 class-validator 装饰器的请求 DTO，只在服务端；
- 两者通过 `implements` 关联：共享类型约束字段名，服务端 DTO 负责校验。

## 7. 前台方案

### 7.1 渲染层（D3）

**默认方案：TypeScript 服务端组件。**

- 每个组件是一个纯函数：`(props: Props) => string`，自动转义；
- 页面 = 组件树 + `PageData`，`PageData` 由 Service 产出并带类型；
- 桌面与移动**同一套组件**，差异通过 props（`variant`）与 CSS 断点表达；
- 交互（换集、抽屉、筛选）保持在独立 JS 模块中，通过 `data-*` 属性挂载，与现在 `app.js` 的模式一致。

**为什么不选 Vue SSR**：内容站几乎不需要客户端渲染，hydration 带来的构建复杂度与首批 JS 体积收益不成比例。若后续出现"用户体系 / 无限滚动 / 弹幕"这类重交互需求，再评估 `apps/site` 独立为 Vue SSR。

**为什么不选模板引擎（Handlebars/EJS）**：那只是把 Liquid 换成另一种无类型检查的模板，P6 的问题原封不动。

### 7.2 路由表（URL 必须保持不变）

| 路径 | 页面 | 现状来源 |
|---|---|---|
| `/` | 首页 | `themes/default/index.liquid` |
| `/today` | 今日更新 | 同上 |
| `/list/:alias` | 分类列表（筛选/分页） | `list.liquid` |
| `/detail/:id` | 详情 | `detail.liquid` |
| `/play/:id/:playId?/:ep?` | 播放 | `play.liquid` |
| `/search` | 搜索 | `search.liquid` |
| `/api/play/:id/:playId/:ep` | 换集数据 | `routes/site/index.ts` |
| 404 兜底 | 错误页 | `404.liquid` |

### 7.3 页面数据契约（示例）

```ts
// packages/shared/src/dto/site.ts
export interface VodCard {
  id: number;
  name: string;
  cover: string;
  remarks: string;
  year: number;
  categoryAlias: string;
}

export interface HomePageData {
  site: SiteInfo;
  nav: NavItem[];
  banner: VodCard[];
  rows: Array<{ title: string; alias: string; items: VodCard[] }>;
}
```

约束：`PageData` 里不许出现 `Date`、`Buffer` 或 Prisma 生成的类型；时间统一为已格式化的字符串。

### 7.4 静态资源

- CSS/JS 从 `apps/server/src/assets` 由静态中间件直出，加长缓存 + 版本号 query；
- `uploads/` 映射到 `/uploads/`（30 天缓存，行为不变）；
- 后续如引入压缩/打包，也只影响构建产物路径，不改 URL。

### 7.5 SEO 不可回退清单

title/description/canonical、OG 标签、面包屑 JSON-LD、sitemap、robots、404 状态码、页面 HTML 完全直出（无 JS 也可读）。

## 8. 迁移路线

每个阶段结束都能独立上线或回滚；未完成前 `master` 保持可用。

### Phase 0 · 地基（0.5 天）

- 建 `v2` 分支（已完成）与本文件；
- 记录前台 7 页的 HTML 快照与后台全部接口的响应样本，作为回归基线；
- 补 `npm run check`（`typecheck + lint + test`）。

**验收**：快照脚本可一键重跑；基线入库。

### Phase 1 · 骨架（1~2 天）

- NestJS 最小可运行：`/healthz`、静态资源、404、异常信封；
- `prisma generate` + `PrismaService`；
- 编译产物可被 PM2 / Docker 启动。

**验收**：容器内 `dist/main.js` 启动成功；`/healthz` 返回 200；旧站点仍由 `master` 提供。

### Phase 2 · 数据层（1 天）

- `db pull` + 校正 + baseline 迁移；
- 补齐 `lcm_vod_merge_ignore`。

**验收**：`prisma migrate deploy` 在空库可完整建表；在现有库上 `migrate status` 为已同步；15 张表字段与索引与 `init.sql` 完全一致（用 `SHOW CREATE TABLE` 逐表 diff）。

### Phase 3 · 后台 API（3~4 天）

- 按 4.4 的模块顺序迁移：auth → settings → categories → vods/plays → lines → sources/rules → tasks/logs → tools → dashboard → upload；
- **后台前端零改动**，靠接口契约不变保证。

**验收**：每个接口与基线响应逐字段 diff 通过；`apps/admin` 不重新构建即可正常使用。

### Phase 4 · 前台页面（3~4 天）

- 先 `PageData` + 组件库，再逐页：404 → search → list → index → detail → play；
- URL、HTML 结构、class 名尽量保持，先求一致再求改进。

**验收**：7 页快照 diff 通过（允许白名单差异：注释、无关属性顺序）；sitemap/robots 一致。

### Phase 5 · 采集与广告（2 天）

- `lib/collect/*`、`lib/ads/*`、`lib/covers/*` 包成 Service；
- 调度器接入 Nest 生命周期。

**验收**：一次完整采集任务成功率与耗时相对基线无退化；中断恢复行为一致。

### Phase 6 · 收尾（1 天）

- 删除 Fastify、Drizzle、liquidjs、`themes/`、`packages/db/src/schema.ts`、`init.sql`；
- 合并桌面/移动两套 CSS 为 tokens + 响应式；
- 更新 `docs/技术方案.md`，使其与 v2 一致；
- 合并 `v2` → `master`，打 tag。

**验收**：`npm run check` 全绿；镜像体积不增大；首屏 TTFB 不高于基线。

## 10. 风险与对策
